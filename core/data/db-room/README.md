# Core Data — Room 3

`core:data:db-room` is the Room 3.0 implementation of the database contracts from
`core:domain`. It is interchangeable with `core:data:db-sqldelight` on Android, Desktop,
iOS, and WasmJS.

## Selecting the implementation

`CORE_DATA_DB_MODULE` in the root `gradle.properties` file is the single source of truth.
`settings.gradle.kts` validates the value and includes only the selected implementation:

```properties
#CORE_DATA_DB_MODULE=:core:data:db-sqldelight
CORE_DATA_DB_MODULE=:core:data:db-room
```

To switch back, exchange the comments. Do not enable both modules: they intentionally expose
the same packages and domain implementations.

After every switch, run the repository verification workflow from `AGENTS.md`:

```bash
./gradle/build_quick.sh
./gradlew :app:android:connectedCheck
./gradlew build
```

Kotlin/Native incremental compilation is disabled in `gradle.properties` because its link
cache retains KLIB identities from the previously selected database module. Gradle's regular
build cache remains enabled, and switching does not require a manual `clean`.

## Room 3 configuration

The module uses the `androidx.room3` Gradle plugin and packages, with
`androidx.room3:room3-runtime`, `room3-compiler`, `room3-paging`, and `room3-testing` at
version 3.0.0. KSP generates the database implementation for Android, JVM, iOS device and
simulator, and WasmJS.

The public `NoteDAO`, `SafeRepo`, and `DatabaseHolder` contracts remain in `core:domain`.
Room DB models are converted to domain models inside `RoomNoteDAO`. Paging is generated by
Room's `PagingSourceDaoReturnTypeConverter`, then mapped by a small domain-model
`PagingSource` wrapper.

## Shared database contract

Both ORM implementations use the same file and v2 schema:

- file name: `notes.db`;
- `PRAGMA user_version = 2`;
- table: `note`;
- columns: `id INTEGER PRIMARY KEY AUTOINCREMENT`, `title TEXT`, `text TEXT`,
  `dateCreated INTEGER`, and `dateModified INTEGER`, all non-null;
- dates: epoch milliseconds;
- ordering: `dateModified DESC`.

Room may add its own metadata table. SQLDelight ignores it, and neither implementation deletes
unknown tables. A raw-SQL compatibility test verifies that Room can read and update the shared
v1 schema, migrate it to v2 without structural changes, and leave it readable after closing.

## Platform drivers and encryption

| Platform | SQLite driver | Encryption |
| --- | --- | --- |
| Android | `SupportSQLiteDriver` over SafeRoom/SQLCipher | SafeRoom encrypt/decrypt/rekey |
| Desktop JVM | `JdbcSQLiteDriver` over `sqlite-jdbc-crypt` | SQLCipher-compatible file conversion and rekey |
| iOS | `IosCipherDriver` over the SwiftPM SQLCipher cinterop | `sqlite3_key`, export, and `sqlite3_rekey` |
| WasmJS | `WebWorkerSQLiteDriver` with SQLite3MultipleCiphers and OPFS | worker-side key/rekey pragmas |

The Android holder uses `TRUNCATE` journaling. Room 3 configures WAL through `SQLiteDriver`, but
that state is not propagated to SafeRoom's `SupportSQLiteOpenHelper`; a cold process start could
otherwise discard committed rows that were still in the previous process' WAL.

Raw SQL is executed through the same active encrypted connection on every platform.

### WasmJS lifecycle

`room3.worker.js` implements the AndroidX SQLite web-worker protocol over the existing
SQLite3MultipleCiphers build. Room uses a single logical connection mapped to the persistent
`notes.db` OPFS file. Each database holder owns its worker. Closing a holder terminates that
worker and yields one browser task before another holder opens the file; this releases the
exclusive OPFS handle without blocking the browser thread in `RoomDatabase.close()`.

Room 3 supplies `WebWorkerSQLiteDriver`, but not a worker implementation. The included worker is
therefore required: it implements the AndroidX protocol while using SQLite3MultipleCiphers rather
than the plaintext SQLite WASM used by the AndroidX example. Before the first Web encryption, the
database is normalized to 4096-byte pages and vacuumed; subsequent password changes use only
`PRAGMA rekey`.

The worker falls back to the regular OPFS database and finally to an in-memory database only
when the corresponding browser capability is unavailable. Production persistence therefore
requires OPFS and cross-origin isolation headers.

## Tests

Focused coverage lives in:

- `src/jvmTest/.../RoomDatabaseIntegrationTest.kt`: CRUD, Flow, Paging, raw SQL, reopen,
  shared v1-to-v2 schema migration, wrong password, encryption, decrypt, and rekey;
- `src/wasmJsTest/.../RoomWebWorkerTest.kt`: worker protocol, CRUD, OPFS reopen, and the complete
  Web password lifecycle;
- `src/androidHostTest`: Room-backed unit-test repository and crypt use-case tests;
- application UI/instrumentation tests: platform encryption and user flows.

Useful focused commands:

```bash
./gradlew :core:data:db-room:jvmTest
./gradlew :core:data:db-room:testAndroidHostTest
./gradlew :core:data:db-room:wasmJsBrowserTest
./gradlew :core:data:db-room:compileKotlinIosSimulatorArm64
```

## Migration rules

- Keep the domain interfaces ORM-neutral.
- Preserve the shared table, column names/types, date representation, database filename, and
  `user_version` when adding migrations.
- Configure KSP for every supported target when changing Room entities or DAOs.
- Test both implementations after schema, encryption, import/export, Paging, or Web worker
  changes.
